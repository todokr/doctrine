# doctrine 概要

- 日付: 2026-09-12（2026-09-13 改訂: 人のレビューと Review Guide を統合）
- 状態: 全体像の確定。コア（サブプロジェクト①）は実装済み（Deno に移行済み、#6）。
  Review Guide（③）は仮説段階であり、③のspec着手時に設計する

このドキュメントは doctrine というプロダクトが**何であり、何でないか**を定める。
個別の設計判断は各specに委ね、ここでは全体像・原則・用語だけを扱う。

## 1. doctrine とは

**ローカルマシンで複数の Claude Code を同時に走らせ、決められた手順で最後まで
走らせきり、その結果を人が理解して承認できる形で差し出すためのデスクトップツール**である。

ユーザーはプロジェクトごとに**ワークフローを宣言的に定義**する
（計画させる → 計画をレビューさせる → 実装させる → テストを流す → 人が変更を理解して判断する
→ PRを作る、など）。
タスクを投げると、常駐デーモンが空いている実行枠を見て順に起動し、
ワークフローの手順に沿ってエージェントを進行させ、人の承認が要る箇所で止まる。

一言でいえば、

> **実装する時間をAIに、判断する責任を人間に残す。**

## 2. 解こうとしている問題

### 2.1 並行実行の管理

Claude Code を複数同時に走らせようとすると、すぐに分からなくなる。

- 何本まで走らせていいのか（マシン負荷とAPIコストの上限）
- 同じリポジトリで衝突しないか
- **どれが自分の承認待ちで止まっているのか**

この3つ目が最も痛い。止まっていることに気づかなければ、並行実行の意味がない。

### 2.2 エージェントに手順を踏ませること

エージェントを素で走らせると、**毎回違う進め方をする**。
テストを流さずに終わることもあれば、確認なくコミットまで進むこともある。

doctrine はここを人の記憶や毎回のプロンプトに任せない。
**ワークフロー定義が手順そのものであり、エージェントはその枠の中でしか動けない。**
「テストが通るまで実装ステップに戻る」「PRを作る前に必ず人の承認を挟む」は
お願いではなく、**エンジンが保証する進行規則**である。

### 2.3 手順はプロジェクトごとに違う

走り終わった後の扱い（コミットする／PRを作る／テストを流す／人が見る）は
プロジェクトによって違う。だから手順は**doctrine に埋め込まず、ユーザーが
宣言的に定義できる**必要がある。

### 2.4 ボトルネックは「書く」から「理解する」へ移る

エージェントによって実装のコストが大きく下がると、人にとってのボトルネックは
**コードを書くこと**から**AIが書いたコードを理解し、正しいと判断すること**へ移る。

並行に走らせるほど、承認待ちには**自分が書いていない差分**が積み上がる。
レビュアーは差分の量だけでなく、

- 何のための変更なのか
- 何が変わったのか（ファイル単位ではなく、概念単位で）
- なぜこの設計なのか
- どこにリスクがあるのか
- どこから読めばよいのか

を毎回自分で組み立てなければならない。ここが詰まれば、2.1〜2.3 を解いても
承認待ちの列が伸びるだけで、並行実行の意味がない。

## 3. 中心の約束 —「投げておいて後で見る」

上の4つを束ねると、doctrine が提供する価値は一文になる。

> **タスクを投げたら、人の判断が要るところまで自動で進む。
> 進んだ結果は後からまとめて、理解して判断できる形で見られる。**

後半の「見る」は、差分を眺めることではない。**人が変更を自分の言葉で説明でき、
その変更に責任を持って承認／差し戻しできる状態**を指す。
doctrine が自動化するのは判断までの作業であり、判断そのものは自動化しない。

この一文は設計判断の判定基準として機能している。
常駐デーモンにしたのも、失敗時にエージェントへ出力を食わせて手順を巻き戻すのも、
承認待ちをひとつの状態として持つのも、レビュー時に読む順序を用意させるのも、
すべてこの約束を成立させるためである。
逆に、この約束に効かない機能は入れない。タスク間の依存関係も、
レート消費率による実行枠の自動調整も、判断に届くまでの速さにも理解のしやすさにも
効かないので入れない（10章）。

## 4. 実現したい姿 — 目標とするワークフロー

具体化すると、最終的にこういうものが回ることを目指している。

1. **毎週月曜10時に起動する**
2. 自分が担当の Linear Issue を取得する
3. Issue を**並列に実行できる粒度に並べ替え、必要ならsub-issue に割る**。
   大きすぎる仕事や人の判断が要る仕事もここで識別する
4. それぞれを doctrine のタスクとして作成する。タスクごとに worktree が切られ、
   以下が進行する
   1. 計画エージェントが作業計画を立案（変更対象・方針・手順・影響範囲・テスト方針・リスク）
   2. 別のエージェントが計画をレビューし、計画エージェントが対応
   3. 実装エージェントが実装
   4. レビューエージェントがコードレビューし、実装エージェントが対応
   5. エージェントが**Review Guide**（人がこの変更を理解するために、何をどの順に読むとよいか）
      を作成する（5章）
   6. doctrine がレビュー画面を開き、ガイド付きのレビューが始まる
   7. 人がレビューする — 修正依頼なら 4-3 へ戻る／承認なら次へ
   8. PRを作成し、ガイドをPR本文に含める
5. PRが承認され次第マージする

注目すべきは **3 と 4-5** である。
「タスクを並べ替えて割る」のも「人が読む順序を用意する」のもエージェントの仕事であり、
doctrine 自身は賢くならない。**doctrine が持つのは、この手順を毎回そのとおりに
踏ませる進行規則と、その状態と成果を見せる面だけ**である。

3 で依存関係のある仕事が見つかった場合も、doctrine は依存を**モデル化しない**。
分解するエージェント（または人）が、依存先が片付くまで後続を投入しない・
1つのタスクにまとめる、といった形で投入順を決める。

### 未確定: ステップ境界を越える成果物

4-1〜4-5 は、**役割の違うエージェントが1つのタスクの中で交代し、前の成果を次が使う**
形をしている。これは①のコア設計が想定する形の延長線上にあるが、2点を
実装計画・③のspecを書く時点で確定させる必要がある。

- **セッションをタスク単位で持つのかステップ単位で持つのか**
  （現在のコア設計specは、タスクが `claude_session_id` を1つ持つ形で書かれている）
- **計画・計画レビュー・コードレビュー・テスト結果の全文を、後段のエージェントに
  どう渡すか**（コアのDBはステップ出力の末尾数KBしか持たない）。
  前段のエージェントが worktree 内にファイルとして書き、後段が読む形なら
  コアを変えずに成立する見込み

## 5. 人のレビューと Review Guide

### AIのレビューと人のレビューは目的が違う

| | AIによるコードレビュー（4-4） | 人によるレビュー（4-7） |
| -- | -- | -- |
| 目的 | コードの品質を上げる | 人が変更を理解し、責任を持って承認できる |
| 出力 | 「ここに問題がある」 | 承認／差し戻し |

だから 4-5 でAIが作るのは、diff の要約でも追加のレビューコメントでもなく、
**変更を理解するためのメンタルモデルを最短で組み立てるためのナビゲーション**である。
AIにレビューさせるのではなく、**AIに「人がレビュー可能な状態」を作らせる**。

### Review Guide が伝えるもの

- **Why** — 今回の実装が何を解決しているか（Issueの写しではなく）
- **What** — 概念単位で何が変わったか
- **How** — 変更後のコードの構造（呼び出しの流れなど）
- **Reading Order** — この順に読むと意図が掴みやすい、という順序。
  ファイル順ではなく概念的な依存（目的 → どこが変わったか → 中心の実装 →
  重要な設計判断 → 境界条件・リスク → テスト）から導く
- **Key Decisions** — 重要な設計判断とその理由
- **Risks** — 人が特に確かめるべき点
- **Tests** — 意図した振る舞いをどのテストが示しているか

入力は git diff だけではなく、**タスクのライフサイクル全体**
（Issue、分解結果、計画、計画レビュー、diff、コードレビュー、テスト結果、リポジトリ構造）である。
特に「なぜこの変更が行われたのか」と「実際に何が変わったのか」を結びつけることが肝になる。

### ガイドは説明ではなく、検証すべき仮説

ガイドの危険は、**もっともらしい説明が人を承認へ誘導すること**である。
Review Guide は鵜呑みにさせるものではなく、

> AIの説明を読む → コードを見る → 説明がコードと一致するか確かめる → 自分のメンタルモデルを作る → 判断する

というループを回すための**仮説の提示**として扱う。「理解した」ボタンを押させること自体を
目的にしない。ガイドが触れていない変更を見落とさせない仕組み（diff に含まれる
ファイルがガイドに現れているかの機械的な照合など）は、③の設計で検討する。

### doctrine との境界

原則「doctrine 自身は賢くならない」「必要になってから入れる」（9章）に従い、

- **ガイドを作るのはワークフロー上のエージェント**である
- **doctrine のコアはガイドの中身を理解しない**。ステップ型も増やさない
- **③ 差分レビューがガイドを表示し、ガイドに沿って diff を読む面を提供する**

データ形式・置き場所・UI は③のspecで決める。

### 段階

最初からインタラクティブなレビュー環境は作らない。

1. **MVP**: エージェントが構造化されたガイドを生成し、簡単なレビュー画面で表示する
2. **将来**: ガイドを1ステップずつ辿る Review Session
   （目的 → 中心の変更 → 設計判断 → 注意点 → 承認／差し戻し）として提供する

## 6. 検証する仮説と成功指標

MVP で最初に確かめるのは次の問いである。

> **AIが生成した Review Guide によって、人がAIの変更を理解する時間と認知負荷は本当に下がるか？**

したがって、PRのマージ数を成功指標にしない。見るのは人の理解コストである。

| 指標 | 意味 | 取り方 |
| -- | -- | -- |
| Review Time | レビュー開始から承認／差し戻しまでの時間 | `approval` ステップの待機開始から解決までを、デーモンが記録から導出できる |
| Misunderstanding / Rework | 「そもそも意図と違う変更だった」という齟齬の頻度 | 差し戻しの割合と差し戻しコメントから近似する |
| Review Preparation Time | 開いてから変更の全体像を掴むまでの時間 | 自己申告 |
| Reviewer Confidence | 「この変更が何をしているか自分の言葉で説明できる」と感じるか | 自己申告 |

利用者は1人なので、比較はガイドの有無による自分自身の読み比べになる。

## 7. 想定する使われ方

- **1人の開発者が、自分のマシンで使う。** マルチユーザーもリモートも想定しない
- **ネットワークには開かない。** IPCはUnixドメインソケットのみ
- **CIの代替ではない。** CIは共有基盤で再現性が要求される。doctrine は個人の
  作業机であり、手元の作業を並行に進めるための道具である
- 対象エージェントは **Claude Code のみ**。汎用エージェントランナーを目指さない

## 8. 全体像 — 4つのサブプロジェクト

| #  | サブプロジェクト  | 内容                                                         |
| -- | --------- | ---------------------------------------------------------- |
| ①  | コア        | ワークフロースキーマ、FSM＋永続化、worktreeライフサイクル、実行枠、Claude Code アダプタ |
| ②  | デスクトップUIシェル | UIフレームワーク選定、カンバン、タスク詳細、コンポーザ                              |
| ③  | 差分レビュー    | Review Guide の表示とガイドに沿ったレビュー、変更/コミット/PRペイン、ファイルツリー付きdiffビューア |
| ④  | HTML生成・編集 | 別エージェントによる静的HTMLレポートおよび注釈つき編集、直接編集                         |

③の内容は、コア設計spec（2章）の表から Review Guide の分を広げてここで定義し直している。

**この順序である理由**: ①は他の3つが乗る土台であり、単独で動作し、単独でテストできる。
②③④はいずれも①の状態を見せる／操作する層にすぎない。
①がUIなしで完結していることが、②以降を自由に作り直せる条件になる。

①には薄いデバッグCLI `dctl` を同梱する。

②③④は着手時にそれぞれspecを書く。

## 9. 横断する設計原則

各specの個別判断は、以下の原則から導かれている。

### 権威ある状態を1箇所に置く

タスクの進行状態を知っているのはデーモンのDBだけである。
Claude Code 側の背景エージェント機構に乗る案を検討して却下したのは、
**2つの状態源を突き合わせる**羽目になるためだった。
同じ理由で、実行枠の占有数もカウンタで持たず `running` を数えて導出する。
カウンタは必ず実体とズレる。

### 設定はデータであって、実行可能コードではない

ワークフロー定義はYAMLで書く。TSにすれば読み込みが任意コード実行になり、
デーモンが信頼境界を跨ぐ。スキーマで検証し、不正な定義は起動時／タスク作成時に落とす。

### 失敗の証拠は消さない

成功したタスクの worktree は削除するが、**失敗・中止したタスクの worktree は残す**。
失敗した実行こそ中を見たい瞬間であり、そこで証拠を消すのは最悪の設計である。
**溜まるのは見えていれば直せるが、消えたものは戻らない。**

### 落ちても最大1ステップしか失わない

ステップ境界ごとに状態を1トランザクションで書く。
デーモンが死んでも、復帰したときに失われるのは進行中の1ステップ分だけである。

**この保証には代価がある。** 復帰時、`command` ステップは頭から再実行される。
つまり doctrine は**「`command` ステップは再実行安全でなければならない」という制約を
ワークフローの書き手に課す**。`pnpm test` は問題ないが `gh pr create` は二重実行になり得る。
検証時に警告は出すが、完全には防げない。

### 対象を1つに絞り、抽象化はテストのために作る

Claude Code アダプタという境界を設けるが、目的は将来の他エージェント対応ではない。
**アダプタをモックしてワークフローエンジンをテストするため**である。
実APIを叩くテストはテストとして成立しない。

### 必要になってから入れる

条件分岐・並列実行・サブワークフロー・依存関係グラフは、いずれも
「あると便利そう」だが中心の約束には効かない。入れない。

## 10. 非ゴール

以下は**やらないと決めたこと**であり、未実装の宿題ではない。

- **人の承認をAIで置き換えること** — AIのコードレビューは品質を上げるためにあり、
  人の判断の代わりではない。doctrine は判断を人に残すために判断までを自動化する
- **タスク間の依存関係** — グラフのスケジューリング、循環検出、依存先失敗時の伝播という
  別の設計が丸ごと必要になり、「並行実行の管理」という中心から外れる
- **レート消費率に応じた実行枠の自動調整** — 記録はするが制御には使わない。
  閾値のチューニングという泥沼が待っている
- **リモート実行・マルチユーザー・チーム共有**
- **Claude Code 以外のエージェント対応**
- **CIの置き換え** — 手順を強制する点はCIに似て見えるが、ゲートする対象が違う。
  CIは共有された push 済みブランチを、人を挟まず再現可能に検査する。
  doctrine は**1人の手元の作業中のブランチ**を、**人の承認をループに含めたまま**進める

## 11. 用語

- **doctrine** — 本プロダクト
- **`dctl` / `dctld` / `.doctrine/`** — CLI・デーモン・プロジェクト設定ディレクトリ
- **タスク** — 1つのワークフロー実行。1つの worktree と1つのブランチを持つ
- **ワークフロー** — 手順の宣言的定義。プロジェクト内にYAMLで置く
- **ステップ** — ワークフロー定義中の1要素。`command` / `agent` / `approval` の3種
- **ステップ実行（step run）** — ステップの1回の試行。失敗時の巻き戻しにより
  同一ステップが複数回実行され得る
- **degraded** — ステップ実行の状態のひとつ。エージェントが権限で操作を拒否されたまま
  「成功」として終わった実行を指す。**成功に見えるが実質何もできていない**状態を
  取り違えないために区別する
- **実行枠（slot）** — 同時に実行中でいられるタスクの数。全体とプロジェクト単位の2スコープ
- **worktree** — タスクごとに切られる git worktree。リポジトリの外に置く
- **Review Guide** — 人が変更を理解するために、エージェントがタスクのライフサイクル全体から
  作るナビゲーション（Why / What / How / Reading Order / Key Decisions / Risks / Tests）。
  doctrine のコアは中身を理解せず、③が表示する
- **Review Session** — Review Guide を1ステップずつ辿る対話的なレビュー。MVPの後に検討する

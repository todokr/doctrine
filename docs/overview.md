# doctrine

このドキュメントは doctrine というプロダクトが**何であるか**を定める。
個別の設計判断は各specに委ね、ここでは全体像・原則・用語だけを扱う。

## 1. doctrine とは

**ローカル環境でエージェントに行わせた作業を、人間が自信を持って理解し、レビューするためのデスクトップツール**である。

レビューする対象となる作業は doctrine 自身が行う。
ユーザーがプロジェクトごとに定義した**ワークフロー**に基づき、 doctrine が作業を進める。
（計画する → 計画を人間にレビューさせる → 実装する → テストを流す → 変更を人間にレビューさせる
→ PRを作る、など）。

タスクを投げると、常駐デーモンが空いている実行枠を見て順に起動し、ワークフローの手順に沿ってエージェントを進行させ、人間の承認が要る箇所で止まる。
止まった作業は、指示・差し戻し・テスト結果といった**経緯と一緒に**レビュー画面に届き、人間はそこで承認か差し戻しかを決定する。

## 2. 解こうとしている問題

### 2.1 ボトルネックは「書く」から「理解する」へ移る

エージェントによって実装のコストが大きく下がると、人にとってのボトルネックは**コードを書くこと**から**AIが書いたコードを理解し、正しいかを判断すること**へ移る。

レビューにおいては、

- 何のための変更なのか
- 何が変わったのか（ファイル単位ではなく、概念単位で）
- なぜこの設計なのか
- どこにリスクがあるのか
- どこから読めばよいのか

を毎回自分で組み立てなければならない。特にエージェントを並列に用いる状況では、これらの把握が負担になる。
この詰まりこそが、AIによる生産性向上を頭打ちにしている課題である。

### 2.2 エージェントに規律を持たせる

エージェントを素で走らせると、**毎回違う進め方をする**。プロンプトで手順を定めたとしても、テストを流さずに終わることもあれば、確認なくコミットまで進むこともあったりと、人間が期待する手順から外れる動きを防ぐことができない。

doctrine はこれをプロンプトに任せない。
**ワークフロー定義が手順そのものであり、エージェントはその枠の中でしか動けない。**
「テストが通るまで実装ステップに戻る」「PRを作る前に必ず人の承認を挟む」など、人間が定めた手順に沿って動くことをエージェントに強制する。

## 3. 提供する価値

doctrine が提供する価値は、

> **エージェントに任せた作業は、事前に定めた手順に沿って進行される。作業の意図や結果は、図表やアニメーション交えた文章など人間の理解にとって最適な形で届き、人間は自信を持って承認や差し戻しの意思決定ができる。結果、人間はアウトプットをすみずみまで理解し、プロダクトのさらなる進化に必要なメンタルモデルを構築することができる。**

doctrine は何のために・何が・なぜ変わったかの理解を人間に促し、判断の理由を人間が自分の言葉で説明できるよう支援することで、これを実現する。

そのため doctrine が自動化するのは最終的な判断までの作業であり、判断そのものは自動化しない。

## 4. 目標とするワークフロー

最終的にこのようなワークフローが回ることを目指している。

1. **毎週月曜10時に起動する**
2. 自分が担当の Linear Issue を取得する
3. Issue を**並列に実行できる粒度に並べ替え、必要ならsub-issue に割る**。
   大きすぎる仕事や人の判断が要る仕事もここで識別する
4. それぞれを doctrine のタスクとして作成する。タスクごとに worktree が切られ、
   以下が進行する
   1. 計画エージェントが作業計画を立案（変更対象・方針・手順・影響範囲・テスト方針・リスク）
   2. 別のエージェントが計画をレビュー（差し戻しは別ステップで計画エージェントが対応）
   3. 実装エージェントが実装
   4. レビューエージェントがコードレビュー（差し戻しは実装エージェントが別ステップで対応）
   5. エージェントが**Review Guide**（人がこの変更を理解するために、何をどの順に読むとよいか）
      を作成する（5章）
   6. doctrine がレビュー画面を開き、ガイド付きのレビューが始まる
   7. 人がレビューする — 修正依頼なら 4-3 へ戻る／承認なら次へ
   8. PRを作成し、本文に要点（Why・What）を、ガイドのデータをPRコメントに載せる
5. PRが承認され次第マージする（レビュアーは `dctl review <PR>` でガイド付きのレビューを行える）

## 5. Review Guide

Review Guide は doctrine が提供する価値の中核をなす重要な機能である。

この機能は、

1. エージェントが行った作業の理解を容易にするため、 hunk を読むべき順番に並び替えてグルーピングし、
2. 解説となるテキストや図表、アニメーションを添え、
3. 人間がインラインあるいは全体に対してのフィードバックをコメントできる

というものである。

解説においては、

- **Why** — 今回の実装が何を解決しているか
- **What** — 概念単位で何が変わったか
- **How** — 変更後のコードの構造（呼び出しの流れなど）
- **Key Decisions** — 重要な設計判断とその理由
- **Risks** — 人が特に確かめるべき点
- **Tests** — 意図した振る舞いをどのテストが示しているか

を提供する。

解説生成の入力には git diff だけではなく、**タスクのライフサイクル全体**（Issue、計画、計画レビューの結果、diff、AIによるセルフコードレビュー結果、テスト結果、リポジトリ構造）を用いる。

説明に際しては文章だけでなく、図やアニメーションを適切に用い、人間の理解を容易にすることが非常に重要である。

## 6. 想定する使われ方

- **作業を走らせるのは、1人の開発者の1台のマシン。** マルチユーザーもリモート実行も想定しない
- **レビューする対象は自分の作業に限らない。**他者が doctrine を利用して作成したPRも、 `dctl review <PR>` でガイド付きで読める
- **デーモンはネットワークに開かない。** IPCはUnixドメインソケットのみ。GitHubを叩くのは
  `dctl` とレビューアプリで、認証は `gh` に委ねる（doctrineは資格情報を持たない）
- **CIの代替ではない。** CIは共有基盤で再現性が要求される。doctrine は個人の
作業机であり、手元の作業を並行に進めるための道具である
- 対象エージェントは **Claude Code のみ**。汎用エージェントランナーを目指さない

## 技術的指針

### doctrine との境界

原則「doctrine 自身はワークフローエンジン」に従い、

- **ガイドを作るのはワークフロー上のエージェント**である。doctrineはガイド作成の組み込みstepを持つ
- **doctrineレビューアプリが diff と作業の経緯を読む面を提供し、③ がそこにガイドの表示とガイドに沿った読み方を重ねる**

### ガイドはPRを通って他者にも渡る

ガイドが置かれる worktree は `completed` で消え、その中身はブランチにも載らない。
つまり**ガイドが残る場所はPRだけ**である。同時に、PRに載ったガイドは自分の読み返しだけでなく
**他人のdoctrineに読ませる受け渡し**にもなる。

- **セルフレビュー（4-7）** — 承認待ちのタスクのレビュー画面。自分の指示で動いたエージェントの
  作業を、経緯と一緒に読み、承認か差し戻しを決める
- **ピアレビュー** — `dctl review <PR>` で開く、他者のPRを読む面。判断はGitHub上の
  approve・コメント・変更要求として送る。差し戻す先が手元に無いので、これはdoctrineの承認とは別物である

PRに載せるのは、人が読む**要点（Why・What）を本文に**、機械が読む**ガイドのデータをPRコメントに**
分けた2つである。図はPRには出さない（GitHubでは変更の印もアニメーションも落ちるため、図はアプリで見る）。

ガイドのデータ形式・置き場所・表示は③のspecで決める。

### MVPと検証

最初の段階で何を作り、何を確かめるかは [mvp.md](./mvp.md) にまとめる。


## 7. 全体像 — 3つのサブプロジェクト


| #   | サブプロジェクト  | 内容                                                                             |
| --- | --------- | ------------------------------------------------------------------------------ |
| ①   | コア        | ワークフロースキーマ、FSM＋永続化、worktreeライフサイクル、実行枠、Claude Code アダプタ                        |
| ②   | レビューアプリ   | タスク一覧のサイドバー、レビュー画面（diff・経緯の表示・ガイドの表示とガイドに沿った読み方の提示・行コメント・承認／差し戻し）、PRを起点にしたピアレビュー（`dctl review <PR>`）、タスク画面、通知とトレイ |

## 8. 横断する設計原則

各specの個別判断は、以下の原則から導かれている。

### 権威ある状態を1箇所に置く

タスクの進行状態を知っているのはデーモンのDBだけである。
同じ理由で、実行枠の占有数もカウンタで持たず `running` を数えて導出する。


### 設定はデータであって、実行可能コードではない

ワークフロー定義はYAMLで書く。TSにすれば読み込みが任意コード実行になり、
デーモンが信頼境界を跨ぐ。スキーマで検証し、不正な定義は起動時／タスク作成時に落とす。

### 失敗の証拠は消さない

成功したタスクの worktree は削除するが、**失敗・中止したタスクの worktree は残す**。
失敗した実行こそ中を見たい瞬間であり、そこで証拠を消すのは最悪の設計である。
**溜まるのは見えていれば直せるが、消えたものは戻らない。**

### 落ちても最大1ステップしか失わない

ステップ境界ごとに状態を1トランザクションで書く。
デーモンが死んでも、復帰したときに失われるのは進行中の1ステップ分だけである。

**この保証には代価がある。** 復帰時、`command` ステップは頭から再実行される。
つまり doctrine は**「`command` ステップは再実行安全でなければならない」という制約を
ワークフローの書き手に課す**。`pnpm test` は問題ないが `gh pr create` は二重実行になり得る。
検証時に警告は出すが、完全には防げない。

### 必要になってから入れる

並列実行・サブワークフロー・依存関係グラフは、いずれも「あると便利そう」だが中心の約束には効かない。入れない。

## 9. 非ゴール

以下は**やらないと決めたこと**であり、未実装の宿題ではない。

- **人の承認をAIで置き換えること** — AIのコードレビューは品質を上げるためにあり、人の判断の代わりではない。doctrine は判断を人に残すために判断までを自動化する
- **レート消費率に応じた実行枠の自動調整** — 記録はするが制御には使わない。
  閾値のチューニングという泥沼が待っている
- **リモート実行とマルチユーザー** — 作業を走らせるのは自分のマシンだけであり、デーモンを
  共有したり他人のタスクを進めたりはしない。**レビューだけは他者のPRにも開く**（6章）
- **Claude Code 以外のエージェント対応**
- **CIの置き換え** — 手順を強制する点はCIに似て見えるが、ゲートする対象が違う。
  CIは共有された push 済みブランチを、人を挟まず再現可能に検査する。
  doctrine は**1人の手元の作業中のブランチ**を、**人の承認をループに含めたまま**進める
- **実行状況を眺めるためのダッシュボード**（カンバン、パイプラインの可視化など） —
  人の仕事はレビューであり、進み具合を眺めることは理解にも判断にも効かない。
  止まっていることに気づく仕組み（通知・トレイ）と、失敗を調べる面だけを持つ
- **doctrine の外で動いたエージェントの作業への差し戻し** — 他者のPRはガイド付きで読める（6章）が、
  そのタスクを進めているのは他人のデーモンであり、こちらから手順の中へ差し戻すことはできない。
  判断はGitHub上の変更要求として送るところまでである。「経緯を知っていることが理解の材料」という
  当初の理由は、**ガイドが経緯の代わりとしてPRに載る**ことで満たす

## 10. 用語

- **doctrine** — 本プロダクト
- **`dctl` / `dctld` / `.doctrine/`** — CLI・デーモン・プロジェクト設定ディレクトリ
- **タスク** — 1つのワークフロー実行。1つの worktree と1つのブランチを持つ
- **ワークフロー** — 手順の宣言的定義。プロジェクト内にYAMLで置く
- **ステップ** — ワークフロー定義中の1要素。`command` / `agent` / `approval` の3種
- **ステップ実行（step run）** — ステップの1回の試行。失敗時の巻き戻しにより
  同一ステップが複数回実行され得る
- **degraded** — ステップ実行の状態のひとつ。エージェントが権限で操作を拒否されたまま
  「成功」として終わった実行を指す。**成功に見えるが実質何もできていない**状態を
  取り違えないために区別する
- **実行枠（slot）** — 同時に実行中でいられるタスクの数。全体とプロジェクト単位の2スコープ
- **worktree** — タスクごとに切られる git worktree。リポジトリの外に置く
- **Review Guide** — 人が変更を理解するために、エージェントがタスクのライフサイクル全体から
  作るナビゲーション（Why / What / How / Reading Order / Key Decisions / Risks / Tests）。
  doctrine のコアは中身を理解せず、③が②のレビュー画面に重ねて表示する。
  タスクの実行中は worktree 内に置かれ、PR を作るときにデータがPRコメントへ、要点が本文へ載る
- **レビュー画面** — ②の中心。承認待ちのタスクについて、作業の経緯・宣言されたファイル・diff を並べ、
  行コメントを付けて承認／差し戻しを決める面（セルフレビュー）
- **ピアレビュー** — `dctl review <PR>` で開く、他者のPRを読む面。ガイドはPRコメントから、diff はPRから読み、
  判断はGitHub上の approve・コメント・変更要求として送る。doctrine の承認／差し戻しとは別物
- **Review Session** — Review Guide を1ステップずつ辿る対話的なレビュー。MVPの後に検討する

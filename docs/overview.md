# doctrine 概要

- 日付: 2026-09-12
- 状態: 全体像の確定。コア設計（サブプロジェクト①）はspec承認済み、実装計画待ち

このドキュメントは doctrine というプロダクトが**何であり、何でないか**を定める。
個別の設計判断は各specに委ね、ここでは全体像・原則・用語だけを扱う。

## 1. doctrine とは

**ローカルマシンで複数の Claude Code を同時に走らせ、決められた手順で最後まで
走らせきるためのデスクトップツール**である。

ユーザーはプロジェクトごとに**ワークフローを宣言的に定義**する
（実装させる → テストを流す → 人が差分を見る → PRを作る、など）。
タスクを投げると、常駐デーモンが空いている実行枠を見て順に起動し、
ワークフローの手順に沿ってエージェントを進行させ、人の承認が要る箇所で止まる。

## 2. 解こうとしている問題

### 2.1 並行実行の管理

Claude Code を複数同時に走らせようとすると、すぐに分からなくなる。

- 何本まで走らせていいのか（マシン負荷とAPIコストの上限）
- 同じリポジトリで衝突しないか
- **どれが自分の承認待ちで止まっているのか**

この3つ目が最も痛い。止まっていることに気づかなければ、並行実行の意味がない。

### 2.2 エージェントに手順を踏ませること

エージェントを素で走らせると、**毎回違う進め方をする**。
テストを流さずに終わることもあれば、確認なくコミットまで進むこともある。

doctrine はここを人の記憶や毎回のプロンプトに任せない。
**ワークフロー定義が手順そのものであり、エージェントはその枠の中でしか動けない。**
「テストが通るまで実装ステップに戻る」「PRを作る前に必ず人の承認を挟む」は
お願いではなく、**エンジンが保証する進行規則**である。

### 2.3 手順はプロジェクトごとに違う

走り終わった後の扱い（コミットする／PRを作る／テストを流す／人が見る）は
プロジェクトによって違う。だから手順は**doctrine に埋め込まず、ユーザーが
宣言的に定義できる**必要がある。

## 3. 中心の約束 —「投げておいて後で見る」

上の3つを束ねると、doctrine が提供する価値は一文になる。

> **タスクを投げたら、人の判断が要るところまで自動で進む。
> 進んだ結果は後からまとめて見られる。**

この一文は設計判断の判定基準として機能している。
常駐デーモンにしたのも、失敗時にエージェントへ出力を食わせて手順を巻き戻すのも、
承認待ちをひとつの状態として持つのも、すべてこの約束を成立させるためである。
逆に、この約束に効かない機能は入れない。

## 4. 実現したい姿 — 目標とするワークフロー

具体化すると、最終的にこういうものが回ることを目指している。

1. **毎週月曜10時に起動する**
2. 自分が担当の Linear Issue を取得する
3. Issue を**並列に実行できる粒度に並べ替え、必要ならsub-issue に割る**
4. それぞれを doctrine のタスクとして作成する。タスクごとに worktree が切られ、
   以下が進行する
   1. 計画エージェントが作業計画を立案
   2. 別のエージェントが計画をレビューし、計画エージェントが対応
   3. 実装エージェントが実装
   4. レビューエージェントがコードレビューし、実装エージェントが対応
   5. レビューエージェントが**「人がこの変更を理解するために、何をどの順に読むとよいか」
      のガイド**を作成
   6. doctrine がレビュー画面を開き、ガイド付きのレビューが始まる
   7. 人がレビューする — 修正依頼なら 4-3 へ戻る／承認なら次へ
   8. PRを作成し、ガイドをPR本文に含める
5. PRが承認され次第マージする

注目すべきは **3 と 4-5** である。
「タスクを並べ替えて割る」のも「人が読む順序を用意する」のもエージェントの仕事であり、
doctrine 自身は賢くならない。**doctrine が持つのは、この手順を毎回そのとおりに
踏ませる進行規則と、その状態を見せる面だけ**である。

### 1ワークフローに複数のエージェントを置くこと

4-1〜4-4 は、**役割の違うエージェントが1つのタスクの中で交代する**形をしている。
これは①のコア設計が想定する形の延長線上にあるが、
**セッションをタスク単位で持つのかステップ単位で持つのかは、
実装計画を書く時点で確定させる必要がある**（現在のコア設計specは、
タスクが `claude_session_id` を1つ持つ形で書かれている）。

## 5. 想定する使われ方

- **1人の開発者が、自分のマシンで使う。** マルチユーザーもリモートも想定しない
- **ネットワークには開かない。** IPCはUnixドメインソケットのみ
- **CIの代替ではない。** CIは共有基盤で再現性が要求される。doctrine は個人の
  作業机であり、手元の作業を並行に進めるための道具である
- 対象エージェントは **Claude Code のみ**。汎用エージェントランナーを目指さない

## 6. 全体像 — 4つのサブプロジェクト

| #  | サブプロジェクト  | 内容                                                         |
| -- | --------- | ---------------------------------------------------------- |
| ①  | コア        | ワークフロースキーマ、FSM＋永続化、worktreeライフサイクル、実行枠、Claude Code アダプタ |
| ②  | デスクトップUIシェル | UIフレームワーク選定、カンバン、タスク詳細、コンポーザ                              |
| ③  | 差分レビュー    | 変更/コミット/PRペイン、ファイルツリー付きdiffビューア                            |
| ④  | HTML生成・編集 | 別エージェントによる静的HTMLレポートおよび注釈つき編集、直接編集                         |

**この順序である理由**: ①は他の3つが乗る土台であり、単独で動作し、単独でテストできる。
②③④はいずれも①の状態を見せる／操作する層にすぎない。
①がUIなしで完結していることが、②以降を自由に作り直せる条件になる。

①には薄いデバッグCLI `dctl` を同梱する。

②③④は着手時にそれぞれspecを書く。

## 7. 横断する設計原則

各specの個別判断は、以下の原則から導かれている。

### 権威ある状態を1箇所に置く

タスクの進行状態を知っているのはデーモンのDBだけである。
Claude Code 側の背景エージェント機構に乗る案を検討して却下したのは、
**2つの状態源を突き合わせる**羽目になるためだった。
同じ理由で、実行枠の占有数もカウンタで持たず `running` を数えて導出する。
カウンタは必ず実体とズレる。

### 設定はデータであって、実行可能コードではない

ワークフロー定義はYAMLで書く。TSにすれば読み込みが任意コード実行になり、
デーモンが信頼境界を跨ぐ。スキーマで検証し、不正な定義は起動時／タスク作成時に落とす。

### 失敗の証拠は消さない

成功したタスクの worktree は削除するが、**失敗・中止したタスクの worktree は残す**。
失敗した実行こそ中を見たい瞬間であり、そこで証拠を消すのは最悪の設計である。
**溜まるのは見えていれば直せるが、消えたものは戻らない。**

### 落ちても最大1ステップしか失わない

ステップ境界ごとに状態を1トランザクションで書く。
デーモンが死んでも、復帰したときに失われるのは進行中の1ステップ分だけである。

**この保証には代価がある。** 復帰時、`command` ステップは頭から再実行される。
つまり doctrine は**「`command` ステップは再実行安全でなければならない」という制約を
ワークフローの書き手に課す**。`pnpm test` は問題ないが `gh pr create` は二重実行になり得る。
検証時に警告は出すが、完全には防げない。

### 対象を1つに絞り、抽象化はテストのために作る

Claude Code アダプタという境界を設けるが、目的は将来の他エージェント対応ではない。
**アダプタをモックしてワークフローエンジンをテストするため**である。
実APIを叩くテストはテストとして成立しない。

### 必要になってから入れる

条件分岐・並列実行・サブワークフロー・依存関係グラフは、いずれも
「あると便利そう」だが中心の約束には効かない。入れない。

## 8. 非ゴール

以下は**やらないと決めたこと**であり、未実装の宿題ではない。

- **タスク間の依存関係** — グラフのスケジューリング、循環検出、依存先失敗時の伝播という
  別の設計が丸ごと必要になり、「並行実行の管理」という中心から外れる
- **レート消費率に応じた実行枠の自動調整** — 記録はするが制御には使わない。
  閾値のチューニングという泥沼が待っている
- **リモート実行・マルチユーザー・チーム共有**
- **Claude Code 以外のエージェント対応**
- **CIの置き換え** — 手順を強制する点はCIに似て見えるが、ゲートする対象が違う。
  CIは共有された push 済みブランチを、人を挟まず再現可能に検査する。
  doctrine は**1人の手元の作業中のブランチ**を、**人の承認をループに含めたまま**進める

## 9. 用語

- **doctrine** — 本プロダクト
- **`dctl` / `dctld` / `.doctrine/`** — CLI・デーモン・プロジェクト設定ディレクトリ
- **タスク** — 1つのワークフロー実行。1つの worktree と1つのブランチを持つ
- **ワークフロー** — 手順の宣言的定義。プロジェクト内にYAMLで置く
- **ステップ** — ワークフロー定義中の1要素。`command` / `agent` / `approval` の3種
- **ステップ実行（step run）** — ステップの1回の試行。失敗時の巻き戻しにより
  同一ステップが複数回実行され得る
- **degraded** — ステップ実行の状態のひとつ。エージェントが権限で操作を拒否されたまま
  「成功」として終わった実行を指す。**成功に見えるが実質何もできていない**状態を
  取り違えないために区別する
- **実行枠（slot）** — 同時に実行中でいられるタスクの数。全体とプロジェクト単位の2スコープ
- **worktree** — タスクごとに切られる git worktree。リポジトリの外に置く

# doctrine ② レビューアプリ設計

- 日付: 2026-09-13
- 状態: 承認済み、実装計画の作成待ち
- issue: [#17](https://github.com/todokr/doctrine/issues/17)
- 前提: [overview](../../overview.md)、[コア設計spec](2026-09-12-agent-orchestrator-core-design.md)

## 1. 位置づけ

doctrine は **ローカルでエージェントにやらせた作業を、人が自信を持って理解し、判断するための
デスクトップツール**である（overview 1章）。人の仕事はレビューであり、②はその面をアプリの中心に据える。

- **①コア** はレビューする対象を生み出す仕組みである。ワークフローを進め、人の承認が要る
  `approval` ステップで止まる
- **②レビューアプリ（本spec）** は、止まった作業を人が理解し、承認か差し戻しを決める面である。
  あわせて、止まっていることに気づく仕組み（通知・トレイ）と、失敗したタスクを調べる面を持つ
- **③Review Guide** は、エージェントが作ったガイドを②のレビュー画面に重ねる

②は当初「デスクトップUIシェル」として、カンバン・タスク詳細・コンポーザを扱う予定だった。
検討の結果、**実行状況を眺める面ではなくレビューする面を中心にする**ことにし、名前と範囲を改めた。
diff ビューアは③から②に移した（6章）。

### 判定基準

機能を入れるかどうかは「**理解と判断に効くか**」で決める（overview 3章）。
カンバン・パイプラインの可視化・「見た」印を入れなかった理由は13章に残す。

### 対象

- **doctrine が実行したタスクだけ**をレビューする。作業の経緯（指示・差し戻し・テスト結果・
  エージェントの最後の発言）を知っていることが、diff だけのツールより深く理解させる材料になり、
  それを持っているのは doctrine が実行したタスクだけだからである。
  差し戻しの行き先（`onReject.goto`）も doctrine のタスクにしかない
- doctrine の外で動いたエージェントの作業（手で動かした Claude Code や Codex のブランチ）は当面扱わない。
  ただし、レビュー画面が読むデータ（9章の `task.diff` / `task.context`）はタスクの内部状態ではなく
  「worktree と基準点」「経緯の列」という形にし、外部の作業を後から受け入れられる形に保つ
- 対象OSは **macOS と Linux（KDE Plasma / Wayland）**

## 3. UIフレームワーク — Tauri に戻す

### 経緯

コア spec 7章は Tauri を推奨し、その後 #6 で Deno Desktop に決めた（デーモンと UI で
ランタイムとツールチェーンを揃えるため）。#6 は Deno Desktop の成熟度の懸念を未再評価のまま残していた。
②着手時に再評価した結果（2026-09-13、Deno 2.9.6 時点）:

- **KDE Plasma 6 / Wayland で `Deno.Tray` がまったく表示されない**
  （[denoland/deno#36502](https://github.com/denoland/deno/issues/36502)、Open、返信なし）。
  開発者本人の環境がこれに当たる
- 懸念されていた「可視ウィンドウが0になるとランタイムが終了する」バグは一次ソースで見つからなかった。
  公式ドキュメントは `hide` してトレイに常駐させる例を載せている。ただし近い既知バグとして、
  Windows WebView2 で hide するとトレイ操作が効かなくなる
  （[#36778](https://github.com/denoland/deno/issues/36778)）、macOS の close / hide まわりの不具合が複数ある
- Deno Desktop は 2.9 でも experimental。single-instance・ログイン時の自動起動の API は見当たらない

**トレイに常駐して承認待ちを知らせる形は②の前提**であり、それが開発者の環境で成り立たない。
Tauri はトレイ・single-instance を持ち、成熟している。

### 変わらないもの

- **デーモンは Deno のまま**。#6 のリライトは戻さない。デーモンを別プロセスに保つ理由
  （ウィンドウを閉じてもタスクが走り続ける／①をUIなしでテストできる）は変わらない
- ワークフロースキーマとイベント型をデーモンと UI で共有する価値（コア spec 7章）も保つ。
  フロントエンドは TypeScript で、`protocol.ts` をそのまま import する

### 代償

Tauri はレンダラから Unix ソケットを開けないので、Rust の中継が要る（4章）。
コア spec 7章の見積もりどおり小さく保つ。

## 4. 構成

```
┌────────────── Tauri アプリ ──────────────┐
│ React (WebView)                          │
│   invoke("rpc", {method, params}) ─┐     │
│   listen("daemon-event")  ◀────┐   │     │
│ Rust: 中継                     │   ▼     │
│   ソケット1本・改行区切りJSON ◀──▶        │
└──────────────────────────┼───────────────┘
                           │ $XDG_RUNTIME_DIR/doctrine/dctld.sock
                     ┌─────┴─────┐
                     │  dctld    │── notify-send / osascript（8章）
                     └───────────┘
```

### Rust の中継は意味を知らない

- `invoke("rpc", { method, params })` を受け、リクエストIDを振ってソケットに1行書き、
  対応する応答を返す
- ソケットから来たイベントは `emit("daemon-event", ev)` でそのまま流す
- **Rust はメソッドの種類を知らない。** デーモンの API が増えても Rust を触らない。
  型はフロントエンドが `protocol.ts` で持つ

### デーモンの起動

- UI 起動時にソケットへ接続できなければ、UI が `dctld` を**切り離したプロセスとして**起動する。
  UI を終了してもデーモンは残る（道連れにしない起動方法は実装計画で確かめる）
- `dctld` は `deno compile` した単一バイナリを Tauri の externalBin として同梱する
- ログイン時の自動起動は持たない。再起動後は UI を開くまでキューが進まないが、
  再起動をまたいで放置することはまれである

### 再接続

- 接続が切れたら、画面上部に「dctld に接続できません — 再接続しています」を出し、間隔を伸ばしながら再接続する
- 再接続したら `task.list` と表示中の画面のデータを取り直す。**イベントの取りこぼしはこの取り直しで吸収する。**
  イベントに連番や再送は持たせない

### 配布

自分でビルドするだけ。署名・公証・自動更新は範囲外。

## 5. 画面構成

プロトタイプ: ブランチ [`prototype/review-app-ui`](https://github.com/todokr/doctrine/tree/prototype/review-app-ui)
（使い捨て。本specで採らなかった「見た」印を含む版なので、画面の構成だけを参照すること）

```
┌──┬───────────────┬──────────────────────────────────┐
│◰ │ 全タスク ▾  ＋ │                                  │
│✓ │ レビュー待ち 4 │                                  │
│⑂ │ ◆ …           │   中央: レビュー待ち → レビュー画面 │
│  │ 要確認 3       │         それ以外     → タスク画面   │
│  │ ! …           │                                  │
│  │ 実行中 3       │                                  │
│⚙ │ 5時間 62% …    │                                  │
└──┴───────────────┴──────────────────────────────────┘
```

### アイコン列

- **タスク**（既定）。レビュー待ちがあれば点を付ける
- **終了**: `completed` / `canceled` をサイドバーに並べる
- **worktree と警告**（第2段階）: 古い worktree か警告があれば点を付ける
- **設定**: エディタ・ターミナルの起動コマンド、古い worktree のしきい値

### サイドバー

| 区分 | 含めるもの | 印 | 時刻の表示 |
| --- | --- | --- | --- |
| レビュー待ち | `suspended` | ◆ | 待ち始めた時刻 |
| 要確認 | `failed`、degraded な実行を持つ非終端タスク、後始末が削除を拒否した `completed` | ! | 経過 |
| 実行中 | `running` | 回転 | 今の状態になってからの経過 |
| 待ち | `queued` | ○ | 優先度と投入からの経過 |
| 一時停止 | `paused` | ‖ | 経過 |

- 各行は **タイトル・プロジェクト（色の点）・時刻**
- 並びは上の表の順。レビュー待ちは古い順（長く待たせているものを上に）
- **レビュー待ちと要確認を分ける。** 人がやることが違い（前者は理解して判断する、後者は原因を調べて対処する）、
  中央に出す画面も違う
- 要確認から外れる条件: 失敗・削除拒否のタスクは **worktree が削除されたとき**に終了へ移る。
  証拠を片付けたことをもって対処済みとみなす（「確認した」操作は持たない）。
  degraded は、タスクが終端状態になったら要確認から外れる
- 削除拒否は `completed` かつ `worktree_path` が非 null で判定できる（イベントを取りこぼしても再起動後に分かる）
- ヘッダーの「全タスク ▾」でプロジェクトを1つに絞り込める。各区分の件数も絞り込みに従う。
  **トレイの件数と OS 通知は常に全プロジェクトを数える**（見逃さないため）
- 最下部にレート制限（第2段階）

### 中央

- レビュー待ちを選ぶと **レビュー画面**（6章）
- それ以外を選ぶと **タスク画面**（7章）

### キー操作

- `j` / `k`: サイドバーの上下
- `n` / `p`: diff の次・前のファイル
- **承認と差し戻しにはキーを割り当てない。** 誤操作の代償が大きく、判断は手でボタンを押す形に残す

## 6. レビュー画面

上から、見出し・経緯・宣言されたファイル・diff・判断の欄を並べる。

### 見出し

タイトル、プロジェクト、ワークフロー、approval ステップの `title`（◆）、何回目のレビューか、
待ち始めてからの時間、ブランチ名。エディタ・ターミナルで開くボタン（第2段階）。

### 経緯

「何が変わったか」だけでなく「なぜそうなったか」「確かめたか」を読むための欄。`task.context`（9章）から作る。

- **元の指示**（`task.prompt`）— 常に表示
- **これまでのレビュー** — 差し戻しコメントと時刻（畳む）
- **直近の `command` ステップの結果** — 終了コードと出力の末尾（畳む）

**エージェントの最後の発言は出さない。** 何をしたつもりかの自己申告はレビューの材料にならず、
先に読むと diff の読み方が引きずられる。何を確かめるべきかは
ガイド（overview 5章「ガイドは説明ではなく、検証すべき仮説」）が持つ。
`task.context` の `lastAgentMessage` は残してあるので、`dctl` からは読める。

### 宣言されたファイル（`review.files`）

計画の承認のように、diff 以外を見て判断するステップがある。approval ステップに見せるファイルを宣言させる。

```yaml
  - id: plan-approval
    type: approval
    title: "計画を確認してください"
    review:
      files: [".doctrine-out/plan.md"]
    onReject:
      goto: plan
      maxAttempts: 3
```

- パスは worktree からの相対パス。絶対パスと `..` を含むものはスキーマ検証で落とす
- `.md` は Markdown として描画し、それ以外は等幅で出す。ファイルが無ければ「ありません」と出す
- 宣言が無ければ diff だけを出す
- 各ファイルは畳める。ファイル名が `plan.md` のものだけ畳んだ状態で出す。承認済みの計画を
  毎回読み直すことはなく、先に読むのは審査結果や実装者の申し送りだから。見るのは名前だけで、
  中身は読まない
- **doctrine はファイルの中身を理解しない。** 計画の置き場所はワークフローの書き手が決める
  （overview 4章で未確定の「成果物の渡し方」を、この項目が縛らない）

### diff

- **範囲**: ベースブランチとの merge-base から **worktree の現在の状態**まで。
  **未コミットの変更と未追跡のファイルを含む。** 承認するのは worktree に実際にあるものであり、
  コミット済みの分だけを見せると、コミットが権限で拒否された（degraded）ケースで取り違える
- **「前回レビュー以降」**: 2回目以降のレビューでは、前回レビュー待ちに入った時点からの差分に切り替えられる。
  差し戻しを繰り返すたびに全体を読み直すのは、overview 2章の「理解のコスト」そのものである。
  基準点の記録方法は9章
- **ビューア**: 左に変更ファイルの一覧（追加・削除の行数）、右に unified 表示とシンタックスハイライト。
  既定は**全ファイルを連続表示**し、一覧を押すとそのファイルへ移る。
  split 表示・前後の行の展開は入れない
- 変更が無い場合（計画の承認など）は「コードの変更はまだありません」と出す

### 行コメントと差し戻し

- diff の行ごとにコメントを書ける。加えて全体へのコメントを書ける
- コメントは**送信前の下書き**として UI 側（アプリのデータディレクトリ）に保存し、アプリを閉じても消さない。
  承認・差し戻しで破棄する
- 差し戻すと、UI が1つの文字列にまとめて **既存の `task.reject(task_id, comment)` で送る**。
  デーモンの API は変えない。形は次のとおり:

```
src/stock/reserve.ts:36
  > return await tx.insert("reservations", { key, orderId, items });
  同時に2つ走ると一意制約違反で落ちます。既存の行として扱ってください

全体: 同時実行のテストも足してください
```

- 差し戻す前に、**送る内容の確認画面**を出す。行コメントがどういう文字列になってエージェントに届くかが見えるので、
  指摘の書き方を合わせられる
- 差し戻しは行コメントか全体コメントが1つ以上あるときだけ押せる（理由の無い却下はエージェントが次にどう動けばいいか分からない。
  コア側も comment 必須）

### 判断の後

承認・差し戻しの後は、サイドバーで**次のレビュー待ちを選んだ状態にする**。溜まったレビューを続けて片付けられる。

### 「見た」状態は持たない

ファイルごとの「見た」印、未確認ファイルの確認ダイアログは入れない。
印を付けること自体が目的化し、overview 5章が避けている「理解したボタン」と同じ罠になる。
**ガイドが触れていない変更を見落とさせない仕組みは③で扱い、②にその素朴な代替は置かない。**

## 7. タスク画面

レビュー待ち以外のタスクを選んだときの画面。パイプラインの図や全ステップの表はメインにしない。

- **状態**、今のステップと何回目か、今の状態になってからの経過
- **止まった理由**
  - `failed`: どのステップで失敗したか。worktree は証拠として残してあることを明示する
  - 削除拒否: 完了時に未コミットの変更が残っていたこと
  - degraded: どのステップが、権限で拒否された操作を含んだまま成功扱いで終わったか
  - `queued`: 行列の何番目か
- **ログ**: 末尾を出す。`running` なら追従する（`task.logs` の follow）
- **実行履歴**: 畳んで置く（`task.get` の `stepRuns`）
- **操作**
  - 第1段階: 中止
  - 第2段階: 一時停止・再開、**同じ内容で投入し直す**、エディタ／ターミナルで開く、パスのコピー、worktree の削除

### 失敗したタスクは再開しない

`failed` は終端状態で、`task.retry` は足さない。足すと `failed → queued` の遷移と、
既存の worktree を上書きするか作り直すかの設計が丸ごと要り、「失敗の証拠は消さない」と衝突する。
代わりに「同じ内容で投入し直す」で、元のタスクのプロジェクト・ワークフロー・タイトル・指示を入れた状態で
コンポーザを開く。元のタスクと worktree は残る。UI 側だけで完結する。

## 8. 気づく仕組み — 通知とトレイ

止まっていることに気づかなければ並行実行の意味がない（overview 2章）。

### 何を知らせるか

| 出来事 | 扱い |
| --- | --- |
| `suspended`（レビュー待ち） | **OS 通知** ＋ 件数に数える |
| `failed` | **OS 通知** ＋ 件数に数える |
| degraded なステップ実行 | **OS 通知** ＋ 件数に数える |
| 後始末が削除を拒否（`task.cleanedUp` の `refused`） | **OS 通知** ＋ 件数に数える |
| `completed` / `canceled` | 知らせない（画面が変わるだけ） |
| 古い worktree | 知らせない（UI で強調するだけ） |

`canceled` は自分の操作の結果である。古い worktree は急ぐものではなく、毎日鳴らせば通知そのものが無視されるようになる。

### 通知はデーモンが出す

**UI が出す形だと、UI を閉じている間は通知が一切出ない。** 「ウィンドウを閉じてもタスクが走り続ける」と同じ筋で、
「UI を閉じていても承認待ちに気づける」ようにする。最も大事な要件を UI フレームワークの出来から切り離す意味もある。

- Linux: `notify-send -a doctrine <title> <body>`（KDE では Plasma の通知サービスが受け取る）
- macOS: `osascript -e 'display notification ...'`（依存を増やさない。発信元が「スクリプトエディタ」と表示され、
  クリックしても doctrine は開かない）
- 文面: `[<project>] <task title> — レビュー待ち: <approval title>` のような形
- 状態遷移ごとに1件1通。**5秒以内に3件以上重なったら**「レビュー待ち 2件 / 失敗 3件」の1通にまとめる
- クリック時の動作は付けない（OS ごとに別の仕組みが要り、見合わない）
- 通知コマンドが見つからない・失敗した場合は `daemon.warning` を1回だけ出し、以後は黙る
- 通知の送出は**アダプタと同じ形で境界を切る**（`Notifier` インターフェース）。テストはモックに対して主張する

### トレイ

- アイコンに**要対応の件数**（レビュー待ち＋要確認、全プロジェクト）を出す
- メニューに要対応のタスクを並べ、選ぶとウィンドウを開いてそのタスクを選ぶ。末尾に「ウィンドウを開く」「終了」
- **トレイから直接承認・差し戻しはさせない。** 中身を見ずに判断する経路を作らない
- ウィンドウを閉じるとトレイに隠れる。完全な終了はトレイの「終了」から（デーモンは止めない）
- macOS はドックのバッジにも件数を出す
- **single-instance**。2回目の起動は既存のウィンドウを前に出す
- ログイン時の自動起動は持たない

### 古い worktree（第2段階）

- 「古い」は、終端状態になってから **7日**（孤児はディレクトリの更新日時から）。しきい値は UI の設定
- デーモンは経過の基準（`age_basis`）を返すだけで判定しない
- worktree と警告のビューで強調し、アイコン列に点を付ける。削除は確認を挟む（未コミットの変更があれば失われる旨を出す）

## 9. コアからの変更点

②はデーモンAPI（コア spec 8章）の上に作る。以下はそれに対する変更である。
**コア spec は書き換えない**方針なので、この節が変更の正本になる。
特に `review.files` は①のワークフロースキーマ（`src/workflow/schema.ts`、`.strict()`）を変える。
**コア spec 3章の approval ステップの記述（`title` / `onReject` のみ）は、この点について承知の上で古いまま残す。**

### イベント

- **追加 `task.cleanedUp`**（#3 の解決。選択肢1を採る）

  ```ts
  { event: "task.cleanedUp"; task_id: string; outcome: "removed" | "refused";
    worktree_path: string | null; warning?: string }
  ```

  - `completed` になったときだけ送る。`tick` の `runTask().then(cleanupAfterRun)` 経路と、
    最終ステップが approval のワークフローで `task.approve` が `completed` にする経路の両方で送る
  - **`task.stateChanged` の後に送ることを保証する**
  - 後始末中の想定外の例外も `refused` と `warning` で届ける
  - `failed` / `canceled` では送らない（worktree を残すのが規則なので `stateChanged` で分かる）
- **追加 `daemon.warning`** `{ event: "daemon.warning"; at: string; message: string; task_id?: string }`
  - 今は stderr に出るだけの `ctx.warnings`（起動時の孤児検出、後始末の失敗など）を UI に届ける
- **変更 `log.line`**: follow は **1接続につき1タスク**とする。`task.logs` を `follow: true` で呼ぶと、
  その接続の追従先を上書きする。`follow: false` で追従をやめる（今は止める手段が無い）。
  `follow: false` が効くのはその `task_id` を追従しているときだけとする。画面の切り替えは
  「前のタスクをやめる」と「次のタスクを追う」を別々に投げるので、無条件にやめると、
  遅れて届いた前者が後者を取り消す

### リクエスト

- **変更 `task.logs`** — `step_run_id` を省けるものとし、省いたときは**最新のステップ実行**の末尾を返す。
  画面は「今のログ」を出すために、先に `task.get` を引いて最後の実行を探す必要がなくなる。
  まだ1度もステップが走っていないタスクは `step_run_id: null` と空の行で返す
- **追加 `daemon.warnings`** — 溜まった警告を新しい順に返す（メモリ上に直近100件。デーモン再起動で消える）。
  UI を後から開いても見えるようにするため
- **変更 `worktree.list`**（#4 の解決。選択肢3を採る）— 孤児だけでなく、**ディスク上にある doctrine の worktree を全部**返す

  ```ts
  { project: string; path: string; branch: string | null;
    task_id: string | null; task_state: TaskState | null;
    dirty: boolean;
    age_basis: string }  // タスクがあれば終端状態になった時刻、孤児ならディレクトリの mtime
  ```

- **変更 `worktree.remove`**（#4）— `task_id` か `path` のどちらか一方を受け付ける
  - `path` は `~/.local/state/doctrine/worktrees/` 配下で、かつ `git worktree list` に出るものに限る
  - **非終端状態（`queued` / `running` / `suspended` / `paused`）のタスクの worktree は `force` でも拒否する**
  - 削除したタスクの `worktree_path` を null にする（要確認から外れる条件、5章）
- **変更 `task.list`** — 各行に `has_degraded: boolean` を足す（サイドバーの要確認の判定に要る）
- **追加 `workflow.list(project)`**（第2段階・コンポーザ用）

  ```ts
  { name: string; default: boolean;
    steps?: { id: string; type: "command" | "agent" | "approval"; title?: string }[];
    error?: string }[]   // steps は setup 挿入後の形。定義が不正なら error
  ```

- **追加 `task.diff(task_id, { since?: "last_review" })`**

  ```ts
  { base: { branch: string; merge_base: string }; since_step_run_id: number | null;
    files: { path: string; old_path?: string; status: "A" | "M" | "D" | "R";
             additions: number; deletions: number; binary: boolean }[];
    patch: string; truncated: boolean }
  ```

  - diff を計算するのはデーモン。worktree の場所とレビューの記録を知っているのはデーモンだけであり（権威は1箇所）、
    Rust の中継を意味を知らないままに保てる
  - 未追跡のファイルを含めるため、一時インデックスで worktree 全体をツリーにしてから比べる
    （`GIT_INDEX_FILE=<tmp> git add -A && git write-tree`）
  - 大きすぎる diff は打ち切って `truncated: true` を返す（上限は実装計画で決める）
- **追加 `task.context(task_id)`**

  ```ts
  { prompt: string;
    reviews: { step_run_id: number; step_id: string; attempt: number;
               decided_at: string; verdict: "approved" | "rejected"; comment: string }[];
    last_command: { step_id: string; exit_code: number | null; stdout_tail: string; stderr_tail: string } | null;
    last_agent_message: string | null;
    review_files: { path: string; content: string | null }[] }
  ```

  - `review_files` は、今の approval ステップの `review.files` をデーモンが worktree から読む（1ファイルの上限は実装計画で決める）

### ワークフロースキーマ

- **approval ステップに `review?: { files: string[] }` を足す**（6章）

### DB

「前回レビュー以降」の基準点と、経緯の履歴は、**どちらも approval ステップの step_run 1件＝レビュー1回**に紐づける。
別々の保存の仕組みではなく、同じ行の2つの列である。

- **`step_runs` に `review_tree TEXT NULL` を足す** — approval ステップで `suspended` に入る時点の worktree 全体のツリー
  （`task.diff` と同じ方法で作る）。`git gc` で消されないよう、
  `refs/doctrine/reviews/<task_id>/<step_run_id>` を指す commit を作って参照を保つ。
  `task.diff({ since: "last_review" })` は、直近の**差し戻された** approval の `review_tree` と現在のツリーを比べる。
  worktree を削除するときに、そのタスクの `refs/doctrine/reviews/` も消す
- **`step_outputs` の主キーを `step_run_id` に変える** — 今は `(task_id, step_id)` で上書きされるので、
  同じステップの2回目が1回目の出力を消し、却下コメントも最新しか残らない。
  経緯（これまでのレビュー）にはすべての回が要る
  - テンプレート変数 `{{ steps.<id>.stdout }}` は今までどおり**そのステップの最新の実行**を指す
  - 末尾 8KB（`OUTPUT_TAIL_BYTES`）の制限は変えない
  - マイグレーションは既存の行を、同じ `(task_id, step_id)` の最新の step_run に割り当てる

### #3・#4 の扱い

#3 は `task.cleanedUp`、#4 は `worktree.list` / `worktree.remove` の変更で解決する。
**本specの PR では設計を決めるだけで、実装は別 PR とし、実装が入った時点で #3・#4 を閉じる。**

## 10. 段階

**レビューが使える状態に最短で着くことを優先する。** タスクを投げる操作は1日に何度も起きるものではなく、
CLI でも回る。レビューは doctrine の価値そのものである。

| 段階 | 含めるもの | それまでの代わり |
| --- | --- | --- |
| **第1段階（MVP）** | サイドバー、レビュー画面（経緯・`review.files`・diff・前回レビュー以降・行コメント・承認／差し戻し）、簡素なタスク画面（状態・止まった理由・ログ・中止）、デーモンの通知、トレイ。9章のうち `task.cleanedUp` / `daemon.warning(s)` / follow の上書き / `task.list` の `has_degraded` / `task.diff` / `task.context` / `review.files` / DB 変更 | — |
| **第2段階** | コンポーザ、worktree と警告のビュー、一時停止・再開、同じ内容で投入し直す、エディタ／ターミナルで開く、レート制限の表示。9章の `workflow.list` / `worktree.list` / `worktree.remove` の変更 | `dctl add` / `dctl worktrees` / `dctl gc` / `dctl pause` など |

第1段階では、失敗・削除拒否のタスクを要確認から外すには `dctl gc` で worktree を消す。

## 11. テスト方針

**守るべきは状態を取り違えないこと（承認待ちを見逃さないこと）であり、見た目の退行ではない。**

- **Rust の中継** — テスト内で偽のソケットサーバーを立てた結合テスト。リクエストと応答の対応、イベントの転送、
  切断と再接続を確かめる
- **フロントエンド** — イベントを受けて状態を更新する処理を純関数（reducer）に切り出し、`deno test` で単体テストする。
  サイドバーの区分の判定、要対応の件数、再接続時の取り直しによる状態の合わせ込み、差し戻しコメントの組み立て
- **デーモン側の変更** — 既存のテストの流儀に従う。特に:
  - `task.cleanedUp` が `stateChanged` の後に届くこと（承認経路を含む）
  - `worktree.remove` が state 配下にないパスと非終端状態のタスクを拒否すること
  - `task.diff` が未コミット・未追跡の変更を含むこと、`since` が直近の差し戻しを基準にすること
  - `step_outputs` の履歴が回ごとに残り、テンプレート変数が最新を指し続けること
  - 通知の分類と、5秒以内の3件以上をまとめること（`Notifier` のモックに対して）
- **画面の E2E テストは書かない。** 1人用のツールであり、見た目の退行は使っていれば気づける

## 13. 検討して採らなかった案

プロトタイプ（5章）で見比べたうえで採らなかったもの。

- **カンバン（列＝ワークフローのステップ）** — ワークフローごとに列が違うので、1枚の板に全プロジェクトを載せられない。
  板を切り替える形では承認待ちが今見ている板の外で起き、定義から消えたステップにいるタスクは板から黙って消える。
  何より、実行状況を眺める面であって、人の仕事（レビュー）の面ではない
- **パイプラインの行（CI 型）＋受信箱** — 板の単位の問題は消えるが、主役が依然として「進み具合」である。
  レビューを中心に置くと、進み具合はサイドバーの区分と時刻で足りる
- **ファイルごとの「見た」印・未確認ファイルの確認** — 6章
- **Deno Desktop** — 3章
- **UI が OS 通知を出す** — 8章
- **`task.retry`** — 7章
- **diff を Rust 側で計算する** — Rust の中継に意味を持たせることになり、worktree とレビューの記録の権威が2箇所に割れる
- **経緯を UI がログファイルから組み立てる** — ログの形式（Claude Code の NDJSON）を UI が解釈することになり、
  アダプタの境界の外に Claude Code 固有の知識が漏れる

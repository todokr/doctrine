# doctrine 利用上限の消費具合をアプリに出す設計

- 日付: 2026-09-19
- 状態: 実装済み
- 前提: [利用上限を待って再開する設計](2026-09-19-rate-limit-wait-design.md)（以下 wait-design）

## 1. 何が問題だったか

Claude の利用上限（5時間枠・7日枠）の利用率は、デーモンが `ratelimit.sample` として
アプリへ送っており、`dctl ratelimit` でも読める。ところがアプリの reducer はこのイベントを
捨てていて、画面からは何も見えなかった。

これは見た目の問題ではなく、**失敗の予告が見えない**という問題である。

- 5時間枠が飽和しても、待てば明ける。`MAX_WAIT_MS` は6時間なので必ず収まり、
  タスクは `rate_limited` で待ってから再開する
- 7日枠が飽和すると `resetsAt` は数日先になり、6時間を超えるので待たずに `failed` になる
  （wait-design 6章で意図して決めた挙動）
- つまり7日枠の飽和はタスクの失敗に直結するのに、それが近づいていることを知る手段が無い。
  実測では1日のうちに7日枠が 0.56 → 0.66 まで上がり、5時間枠は一度 1.00 に達した

## 2. 決定の要約

| 論点 | 決定 |
| --- | --- |
| 置き場所 | サイドバー最下段に常時表示。トーストには寄せない |
| 7日枠の別扱い | 色（7日枠だけが警告色・危険色になる）、説明文（警告に入ったら失敗に直結すると書く）、位置（下） |
| 7日枠の警告の閾値 | 利用率 0.8（`WEEKLY_WARN_UTILIZATION`）。`SATURATED_UTILIZATION`（1）とは別の値 |
| `resets_at` の変換の置き場 | デーモンの境界（`handlers.ts`）。イベントと RPC 応答を作る所で ISO 8601 か null に揃える |
| 開いた直後の値 | `ratelimit.recent` で埋める（backfill） |

## 3. `resets_at` の変換はデーモンの境界に置く

### 3.1 生の値は1つの形をしていない

`rate_limit_samples.resets_at` は TEXT 列で、`insertRateLimitSample` はアダプタが素通しした値を
そのまま bind する。claude が `resetsAt` を JSON の数値で出すと、保存される値は
`"1789828800.0"`（小数付きの epoch 秒の文字列）になる。したがって同じ値が、
**実行中のイベントでは数値、DB 経由で読むと小数付きの文字列**であり、ISO 8601 の文字列で
来ることもある（wait-design 5.1 の実測）。`protocol.ts` の `string | null` という注釈は、
正規化する前は実態と合っていなかった。

`parseResetsAt` は当初、数字の文字列を `/^\d+$/` で判定していて小数付きの形を読めなかった。
`/^\d+(\.\d+)?$/` に広げた。これは表示のためだけではなく、`classifyRateLimit` の代替根拠
（wait-design 5.4）も同じ関数を通るためで、帰結は wait-design 5.4 に書いた。

### 3.2 どこで1つの形に寄せるか

`handlers.ts` が `ratelimit.sample` を配る前と `ratelimit.recent` を返す前に、
`normalizeResetsAt`（`parseResetsAt` の結果を ISO 8601 か null にするだけの関数）を通す。
`dctl ratelimit` の出力も同じ形になる。DB の列と書き込み経路には触らない。

- 生の値が数値にも小数文字列にもなることを知っているのはデーモンだけである。その知識を
  境界の外に出さなければ、読む側が増えても解釈は1箇所で済む
- `protocol.ts` には `rate_limited_until`（ISO 8601）という前例がある。同じイベント群の中で
  時刻の形が2種類あると、読む側が取り違える
- アプリは他の時刻と同じ `parseTime` で読める

採らなかった案:

- **アプリが core の `parseResetsAt` を import する**: `rateLimit.ts` の型依存（`db/schema.ts`
  経由の kysely）がアプリの tsc に入ってくる
- **`parseResetsAt` を shared へ移す**: 「アプリも生の値を解釈する」という構図が残る

アプリ側は、版のずれで生の値が届いても `Invalid Date` を出さないように、読めない `resets_at` を
`null`（「明ける時刻は不明」）として扱う。独自の解釈はしない。

## 4. 置き場所は常時表示にする

`daemon.warning` のトーストには寄せない。

- トーストは文字列1枠で、別のトーストに上書きされ、2.6秒で消える
- 標本は「出来事」ではなく「今の状態」である。次のタスクを投げてよいかを決めるときに
  見られなければ意味が無い
- 閾値を超えるたびにトーストを出すと、標本は agent ステップの間くり返し届くので連打になる

サイドバーの一覧の下（`side-scroll` の後ろ）に、枠ごとに1行ずつ出す。標本が1件も無いときは
その旨を出し、まだ届いていない枠の行は出さない。未知の枠（claude が枠を増やした場合）は
捨てずに、生のキーのまま既知の枠の後ろに出す。

## 5. 7日枠を5時間枠と同じ見た目にしない

| | 5時間枠 | 7日枠 |
| --- | --- | --- |
| 色 | いつも既定色 | 0.8 以上で警告色、1 以上で危険色 |
| 説明文 | 1.00 のときだけ「新しいタスクは明けるまで始まりません」 | 警告以上のとき「飽和すると…タスクは待たずに失敗します」 |
| 位置 | 上 | 下 |
| 明ける時刻 | 時分（`hm`） | 日付つき（`clock`） |

- **5時間枠は 1.00 でも警告色にしない。** 飽和したときの行き先は「上限待ち」であって失敗ではない。
  ただし飽和中は新しいタスクが admit されない（wait-design 6章）ので、その1点だけを中立の
  文言で伝える
- **7日枠の説明文は警告に入ったときだけ出す。** 常に出すと読まれなくなる
- **閾値を `SATURATED_UTILIZATION` と共有しない。** あちらはデーモンが反応する点（使い切った瞬間）で、
  こちらは人に予告する点である。飽和してから知らせるのでは遅い、というのがこの設計の主題なので、
  同じ定数にはできない
- **時刻の書式を変える。** `hm` は「今日か明日かまでは出さない（数時間先までしか待たない）」と
  決めてある関数で、数日先の時刻に使うと嘘になる。5時間枠のほかは `clock` で日付を添える
- **もう明けた枠**（`resetsAt` が現在以前）は「明けました」と出し、利用率は古い値として弱く出す。
  警告もしない。明けた後の実際の利用率は次の標本まで分からない
- どの行にも、いつ観測した値か（「3分前」）を添える。何時間も前の値を今の値と読ませない

区分・文言・書式は `model.ts` の `rateLimitViews` が決め、表示部品は値を組み立てない。

## 6. 開いた直後の値は `ratelimit.recent` で埋める

`ratelimit.sample` は agent ステップが走っている間しか飛ばない。イベントだけに頼ると、
アプリを開いた直後は空欄で、直前の実行が何時間か前なら、いちばん知りたいとき
（次のタスクを投げてよいか）に何も出ない。

15秒ごとの取り直しで `ratelimit.recent` を呼ぶ。`limit` は渡さず、デーモン既定の 50 行を取る。
この RPC は枠の混ざった直近 N 行を返すので、枠ごとの最新1件に畳むのは reducer の役目である。

反映は `sync` とは別の action（`limits.recent`）で、**枠ごとに観測時刻の新しいほうを残すマージ**にする。
`sync` に相乗りさせて代入すると、イベントで届いたばかりの値を、取り直しのたびに DB の古い行で
上書きしてしまう。`ratelimit.sample` のほうは届いた順が新しい順なので、常に置き換える。

`ratelimit.recent` が失敗しても、タスクの一覧の取り直しは止めない。

## 7. フィクスチャ

アプリにはデモモードが無い（`fixtures.ts` は画面からは使わない）ので、「アプリ単体で確認できる」は
デーモン無しで reducer に流して確かめられる、という意味に取る。`ServerEvent[]` を2組置く。
値はデーモンが正規化した後の形（ISO 8601）で書く。

- `RATELIMIT_NORMAL` — 5時間枠 0.22 / 7日枠 0.66。どちらも平常
- `RATELIMIT_NEAR_SATURATION` — 5時間枠 0.80 / 7日枠 0.86。7日枠だけが警告に入る。
  7日枠を実測の 0.66 にすると閾値に届かず、この設計の主題である別扱いが一度も見えない

## 8. やらないこと

- **飽和の手前で新規タスクの投入を絞る制御。** `SATURATED_UTILIZATION` は 1 のままにする。
  スケジューラの方針の話なので別タスク
- **`maxConcurrent` の既定値の見直し**
- **閾値を超えたときの通知**（トースト・OS通知・トレイ）。常時表示までに留める
  （wait-design 10章の「上限待ちの通知はしない」と同じ方針）
- **利用率の履歴・推移グラフ。** 持つのは枠ごとの最新1件だけ
- **`rate_limit_samples` の形と書き込み経路の変更**
- **`utilization` から残り時間や残り回数を予測すること。** 推測した数字は当たらないし、
  外れたときに「予告が見える」という目的を裏切る
- **`rate_limit_info.status` を使うこと**（wait-design 5.1 のとおり飽和時の値が未観測）

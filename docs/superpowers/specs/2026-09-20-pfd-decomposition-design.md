# PFD による Issue の分解 — doctrine の前段

- 日付: 2026-09-20
- 状態: 実装済み
- 前提: [overview](../../overview.md) 4.1 の手順 3（Issue を PFD で分解する）

## 1. 位置づけ

overview 4 章は、Issue を doctrine のタスクにする前に、並列に実行できる粒度に分解し、
大きすぎる仕事や人の判断が要る仕事を識別する工程を置いている。

本 spec はその工程の中身を **PFD（Process Flow Diagram）** で定める。PFD は清水吉男氏が考案した
作業プロセスの設計記法で、要素は「成果物」と「プロセス」の 2 種類しかない。プロセスは成果物を
入力に取り、別の成果物を出力する。プロセス同士・成果物同士は直接つながらない。

PFD をこの工程に使う理由は 1 つである。**「いま着手できるプロセスはどれか」が図から機械的に決まる。**
入力の成果物がすべて揃ったプロセスは着手でき、互いに待ち合わせる必要のないプロセスは並列に走る。

この仕組みは **doctrine の外**に置く。doctrine のコア（`core/`）とアプリ（`app/`）は PFD を知らない。
doctrine との接点は `dctl add` と `dctl ls` の 2 つのコマンドだけである。

doctrineの外側に置くのは、構想がうまくワークするかを判断するための一時的な簡易の対処である。ワークすることがわかれば、doctrine本体に組み込む。

## 2. 決定の要約


| 項目             | 決定                                                                 | 章   |
| -------------- | ------------------------------------------------------------------ | --- |
| 成果物の受け渡し       | 成果物とは「baseBranch にマージされたもの」。入力が揃ったプロセスだけをタスクにする                    | 4   |
| 実行場所           | すべて doctrine の外。分解と PFD のレビューは Claude Code のスキル、決定論的な処理は CLI `pfd` | 5   |
| 正本の形式          | YAML。図は YAML から生成する                                                | 6   |
| 正本の置き場所        | doctrine の状態ディレクトリ配下（リポジトリの外）                                      | 6   |
| sub-issue      | 作らない。プロセス 1 つ ＝ doctrine タスク 1 つ ＝ PR 1 つ                          | 3   |
| 再投入の契機         | 人が `pfd dispatch` を叩く                                              | 7   |
| 粒度             | 4 条件をすべて満たすところで分解を止める                                              | 8   |
| doctrine コアの変更 | なし                                                                 | 5   |


## 3. 全体の流れ

外側の流れ自体を PFD で書く。`[ ]` が成果物、`( )` がプロセスである。

```
[GitHub Issue]──┐
[リポジトリ]────┼─▶(P1 PFD で分解する)─▶[PFD (案)]
                                          │
                        (P2 人が PFD をレビューする)
                                          │
                                   [承認済み PFD]──┐
                                                   ▼
 [マージ済みの成果物]───────────▶(P3 入力が揃ったプロセスをタスクにする)
        ▲                                          │
        │                                  [doctrine タスク]
        │                                          │
 (P5 PR をレビューしてマージする)       (P4 doctrine が実行する ※既存)
        ▲                                          │
        └─────────────────[PR]◀────────────────────┘
```


| #   | プロセス        | 担い手            | 完了条件                                     |
| --- | ----------- | -------------- | ---------------------------------------- |
| P1  | PFD で分解する   | エージェント（スキル）    | `pfd validate` が通る                       |
| P2  | PFD をレビューする | 人              | 人が承認し、`pfd approve` が記録される。差し戻しなら P1 へ戻る |
| P3  | タスクにする      | `pfd dispatch` | 入力が揃った未投入のプロセスが、すべて doctrine タスクになっている   |
| P4  | 実行する        | doctrine       | プロジェクトのワークフローが終わり、PR ができている              |
| P5  | マージする       | 人              | PR が baseBranch に入っている                   |


P3〜P5 は、PFD の末端の成果物がマージされるまで繰り返す。

対応関係は次のとおり。


| PFD                | 対応先                                      |
| ------------------ | ---------------------------------------- |
| プロセス               | doctrine タスク 1 つ、PR 1 つ                  |
| プロセス定義（目的・手順・完了条件） | タスクの `prompt`                            |
| 成果物定義（何であるか・確かめ方）  | 入力側はタスクの前提として、出力側は受け入れ条件として `prompt` に載る |
| 成果物が「揃った」          | それを出力するプロセスの PR が baseBranch にマージされた     |
| 階層分解               | 粒度の条件（8 章）を満たさないプロセスを、P1 の中でさらに割る        |


## 4. 成果物はマージで受け渡す

doctrine のタスクは互いに独立している。`tasks` テーブルに依存を表す列は無く、スケジューラは
`queued` のタスクを優先度順に拾うだけである。`.doctrine-out/` による受け渡しは 1 タスクの
worktree の中に閉じている。したがって、あるプロセスの出力を別のプロセスが受け取る経路は
doctrine の中には無い。

本 spec は経路を足さない。**成果物を「baseBranch にマージされたもの」と定義する。** doctrine は
タスクごとに baseBranch から worktree を切るので、上流の PR がマージされた後に作られた下流のタスクは、
何もしなくても上流の成果物を持った状態で始まる。

代償は、依存の連鎖がマージ待ちで直列になることである。人の PR レビューが連鎖の各段に挟まる。
これは受け入れる。doctrine は判断を人に残すための道具であり、人が見ていない成果物の上に
次の作業を積むことは、その目的と逆を向いている。

例外は、人が出す成果物（6.3）である。人が決めた内容はコードではないので、マージではなく
`pfd done` の記録として受け渡す。

この定義は粒度の条件（8 章）にも効く。どのプロセスの出力も、**単独でマージして baseBranch が
壊れない**ものでなければならない。

## 5. 構成 — スキルと CLI

判断が要る部分と、決定論的に済む部分を分ける。


| 部品        | 担うこと                                                  | 形                |
| --------- | ----------------------------------------------------- | ---------------- |
| `pfd` スキル | P1（Issue とリポジトリを読んで PFD を書く）と P2 の進行（図を人に見せ、指摘を受けて直す） | Claude Code のスキル |
| `pfd` CLI | 検証・図の生成・承認の記録・投入・状態の表示                                | Deno 製の CLI      |


スキルは PFD の YAML を書く以外の副作用を持たない。検証と図の生成は自分でやらずに CLI を呼び、承認・投入・人のプロセスの完了は人に任せる。
エージェントが「検証したつもり」「投入したつもり」で終わる余地を残さないためである
（overview 2.2 と同じ理由）。

CLI はリポジトリのルートに `pfd/` として置き、`core/` `app/` と並べる。依存の向きは
`pfd → dctl`（コマンドとして呼ぶ）の一方向だけで、`core/` のソースは import しない。
状態ディレクトリの場所だけは doctrine と同じ規則（`DOCTRINE_STATE_DIR`、無ければ
`~/.local/state/doctrine`）で求める。

```
pfd path     <project> <issue>   # pfd.yaml の場所を表示する（ディレクトリが無ければ作る）
pfd validate <project> <issue>   # 構造の検証（6.2）
pfd render   <project> <issue>   # 図を生成してブラウザで開く
pfd approve  <project> <issue>   # 人が承認したことを記録する
pfd dispatch <project> <issue>   # 入力が揃った未投入のプロセスを dctl add する（7 章）
pfd status   <project> <issue>   # 各プロセスの状態を表示する
pfd done     <project> <issue> <process-id> --note <text>   # 人が行うプロセスを完了にする（6.3）
```

`<project>` は対象リポジトリのルートのパス、`<issue>` は GitHub Issue の番号である。スキルは
`pfd path` で得た場所に `pfd.yaml` を書く。

`pfd approve` は人のためのコマンドである。検証を通した上で PFD の要約を示し、端末から `y` の入力を
受けて初めて承認を記録する。標準入力が端末でなければ何もせずに失敗する。エージェントが自分の書いた
PFD を自分で承認する経路を塞ぐためである。

## 6. PFD の正本

### 6.1 形式と置き場所

正本は YAML である。図は `pfd render` が YAML から生成するもので、正本ではない。

```
<状態ディレクトリ>/pfd/<プロジェクトのキー>/<issue 番号>/
├── pfd.yaml        ← 正本。P1 が書き、P2 で人が承認する
└── dispatch.json   ← 投入の記録。pfd CLI だけが書く
```

`<プロジェクトのキー>` は、リポジトリのディレクトリ名に、その絶対パスのハッシュの先頭 8 文字を
付けたものである（例: `doctrine-3fa9c1d2`）。同じ名前のリポジトリが別の場所にあっても衝突しない。

人が承認した設計（`pfd.yaml`）と、機械が書く進行の記録（`dispatch.json`）を別のファイルにする。
承認後に `pfd.yaml` が書き換わっていたら、承認は無効になる（`dispatch.json` に承認時の
ハッシュを持ち、`pfd dispatch` が照合する）。

リポジトリの外に置くので、PFD はそのマシンにしか無い。doctrine は 1 人の 1 台のマシンで動かす
道具であり（overview 6 章）、この制約はそれと揃っている。

```yaml
issue: 123
title: 利用状況の集計を画面に出す
goal: [feature]            # この成果物がマージされたら Issue は完了

artifacts:
  - id: schema
    name: 既存スキーマ
    given: true            # 最初から baseBranch にある
  - id: new-table
    name: 集計テーブル
    description: 日次の利用回数を持つテーブルとマイグレーション
    verify: マイグレーションが適用でき、テーブル定義のテストが通る
  - id: metric-definition
    name: 集計の定義
    description: 何を 1 回の利用と数えるか
    verify: 人が決めた内容が pfd done の --note に書かれている
  - id: endpoint
    name: 集計 API
    description: ...
    verify: ...
  - id: feature
    name: 集計画面
    description: ...
    verify: ...

processes:
  - id: "1"
    name: マイグレーションを書く
    inputs: [schema]
    outputs: [new-table]
    purpose: ...
    steps: ...
    done_when: ...
  - id: "2"
    name: API を実装する
    inputs: [new-table, metric-definition]
    outputs: [endpoint]
    purpose: ...
    steps: ...
    done_when: ...
  - id: "3"
    name: 集計の定義を決める
    actor: human           # 人の判断が要る。タスクにしない
    inputs: [schema]
    outputs: [metric-definition]
    purpose: ...
    done_when: ...
  - id: "4"
    name: 画面を繋ぐ
    inputs: [endpoint]
    outputs: [feature]
    purpose: ...
    steps: ...
    done_when: ...
```

この例では、最初に着手できるのはプロセス 1（エージェント）と 3（人）である。2 は両方の出力を待つ。

プロセスは成果物の id だけを参照し、他のプロセスを参照しない。「成果物とプロセスを交互につなぐ」
という PFD の規則は、この形式では破りようがない。

### 6.2 検証

`pfd validate` は次を確かめる。どれかに反したら、どの id が何に反したかを示して非 0 で終わる。

- すべてのプロセスに、入力と出力がそれぞれ 1 つ以上ある
- 参照されている成果物がすべて定義されている
- どの成果物も、出力するプロセスは高々 1 つである
- `given: true` でない成果物には、出力するプロセスがある
- `given: true` の成果物を出力するプロセスは無い
- `goal` でない成果物は、どれかのプロセスの入力になっている（誰にも使われない成果物が無い）
- 循環が無い
- `goal` の成果物に、`given` の成果物から辿り着ける
- `given` でない成果物のすべてに `verify` がある
- `actor: agent`（既定）のプロセスのすべてに `purpose` `steps` `done_when` がある

### 6.3 人の判断が要るプロセス

overview 4.1 の手順 3 は、人の判断が要る仕事を分解の時点で識別するとしている。PFD ではこれを
`actor: human` のプロセスとして書く。`pfd dispatch` はこれをタスクにしない。`pfd status` は
入力が揃った `actor: human` のプロセスを「あなたの番」として示し、人は済ませたら `pfd done` で
完了にする。

人が出した成果物の中身（決めた内容）は、下流のタスクに届かなければ意味が無い。`pfd done` は
`--note <テキスト>` または `--note-file <パス>` を必須とし、その内容を `dispatch.json` に記録する。
`pfd dispatch` は、この成果物を入力に取るプロセスの prompt に内容をそのまま載せる（7.2）。
決めた内容がリポジトリ内のファイルとしてすでにコミットされているなら、note にはその場所を書けばよい。
`pfd done` も `pfd approve` と同じく人のためのコマンドであり、標準入力が端末でなければ失敗する。

「大きすぎる仕事」は別の扱いになる。粒度の条件（8 章）を満たさないプロセスは P1 の中で
割りきるものであり、割りきれないまま残ったプロセスがあれば、それは P2 で人が差し戻す理由になる。

## 7. 投入 — `pfd dispatch`

`pfd dispatch` は、承認済みの PFD を読み、次の条件をすべて満たすプロセスを doctrine タスクにする。

- `actor: agent` である
- まだ投入されていない
- 入力の成果物がすべて揃っている

成果物が揃っているとは、次のいずれかである。

- `given: true` である
- それを出力するプロセスが `actor: agent` で、そのタスクのブランチを head とする PR がマージ済みである
（`gh pr list --head <branch> --state merged`）
- それを出力するプロセスが `actor: human` で、`pfd done` が記録されている

PR のマージ先が baseBranch かどうかは見ていない。pfd は baseBranch を知らないためである。

この判定は、**タスクのブランチから PR が作られること**を前提にしている。doctrine はそれを保証しない。
PR を作るかどうかはプロジェクトのワークフロー次第であり、`dctl project-add` が作る雛形の
ワークフローは PR を作らない。タスクが `completed` になると worktree は消えるがブランチは残るので、
PR の作り方は 2 通りある。

- ワークフローの最後のステップで作る（overview 4.2 の手順 8）
- タスクが `completed` になった後、人が残ったブランチから作る

どちらも無ければ、下流のプロセスはいつまでも入力待ちのままになる。`pfd status` は、タスクが
`completed` なのにブランチに PR が無いプロセスを、それと分かるように示す。

マージの判定に git の祖先関係（`git merge-base --is-ancestor`）は使わない。squash マージされた
ブランチは baseBranch の祖先にならないためである。

### 7.1 何度実行してもよい

`pfd dispatch` は人が何度も叩く。上流の PR をマージするたびに叩き、叩き忘れたと思えばまた叩く。
したがって、**同じプロセスを 2 回タスクにしてはならない。**

`dctl add` は再実行安全ではない。`dctl add` が成功した直後、`dispatch.json` に書く前に
プロセスが落ちると、記録の上では未投入のままタスクだけが存在する。これを避けるため、
投入済みかどうかの判定は `dispatch.json` だけに頼らない。

- タスクのタイトルの先頭にキーを付ける: `[pfd:123/2] API を実装する`
- `pfd dispatch` は投入の前に `dctl ls --project <path>` を読み、同じキーを持つタスクがあれば
投入せず、そのタスクの id を `dispatch.json` に書き戻す

### 7.2 タスクに渡す prompt

プロセス定義と、入出力の成果物定義から組み立てる。

```
<親 Issue の URL とタイトル>

この作業は、上の Issue を分解したうちの 1 つである。

## 目的
<purpose>

## 前提
すでに baseBranch にあるもの:
- <入力の成果物の name>: <description>

人が決めたこと:
- <人が出した入力の成果物の name>: <pfd done の note の内容>

## 作るもの
- <出力の成果物の name>: <description>
  確かめ方: <verify>

## 手順
<steps>

## 完了条件
<done_when>

## 範囲
この作業の出力は上の「作るもの」だけである。Issue の残りの部分は別の作業が担う。
```

ワークフローは `dctl add` の既定（プロジェクトの `defaultWorkflow`）に任せる。プロセスごとに
ワークフローを変えたくなったら、プロセス定義に `workflow` を足す。今は足さない。

## 8. 粒度 — どこで分解を止めるか

プロセスは、次の 4 つをすべて満たすところまで割る。スキルが P1 で使う基準であり、
人が P2 で PFD を見るときの観点でもある。

1. **人が一度でレビューしきれる PR 1 つに収まる。** doctrine の価値はレビューできることにある
2. **エージェントが 1 回の実行でやりきれる。** 計画 → 実装 → レビューの 1 周で終わる量である
3. **単独でマージしても baseBranch が壊れない。** 成果物をマージで受け渡す（4 章）ための必須条件
4. **出力の成果物が単独で検証できる。** 成果物定義の `verify` に、その成果物だけを確かめる方法が書ける

3 と 4 は、プロセスの切り方を縛る。「API の前半を書く」のような切り方は、出力が単独で検証できず、
マージすれば壊れるので、プロセスにならない。未使用のまま入れておけるもの（テーブル、部品、
フラグの裏に置いた機能）が切れ目になる。

## 9. 図

`pfd render` は YAML から Mermaid を生成し、それを埋め込んだ HTML を状態ディレクトリに書いて
ブラウザで開く。Mermaid 本体は CDN から読むので、図を見るにはネットワークが要る。成果物は四角、プロセスは丸で描く。`actor: human` のプロセスは見た目で区別する。
承認済みなら、プロセスを状態（完了・実行中・着手可能・入力待ち）で塗り分ける。

図は人が `pfd render` を叩いたときにだけ作られる。

## 10. 決めていないこと

- **タスクが `failed` / `canceled` で止まったプロセス。** 同じキーのタスクがすでにあるので、
`pfd dispatch` は投入し直さない。`pfd status` はそれと分かるように示すだけで、やり直す手順は
最初の版では用意しない。抜け道は、pfd.yaml でそのプロセスの id を変えて（例: `2` → `2b`）承認し直すことである。doctrine はタスクを消せないので、同じ id のままでは古いタスクが拾われ続ける。PFD を作り直すときも、投入済みのプロセスの id を使い回さない
- **PFD の記法の出典。** 6 章の規則は PFD の一般的な説明に基づく。AFFORDD の「PFD の書き方」に
照らして、用語と規則を確かめる
- **承認後に PFD を直したくなったとき。** 実行が進んでから分解の誤りに気づく場合がある。
投入済みのプロセスを保ったまま残りを直す手順は、最初の版では用意しない（PFD を作り直す）
- **スキルの配布。** スキルは `pfd/skill/pfd-decompose/` に同梱し、利用者が `~/.claude/skills/` へ
シンボリックリンクを張る。プラグインとして配る形は、利用者が自分以外に増えてから考える
- **Linear の Issue。** overview 4 章は Linear を想定している。最初の版は GitHub Issue だけを扱う

1 つのタスクにするには大きい Issue は、PFD（成果物とプロセスの図）に分解し、入力が揃ったプロセスから順に doctrine のタスクにする。今はアプリの Intake ビューで、分解・承認・投入を行う。PFD の正本はデーモンの SQLite にあり、リポジトリにはコミットされない。

`dctl` の intake コマンドは読むものだけである。開始・回答・承認・人のプロセスの完了は、アプリからしかできない。

```bash
dctl intake ls [--project <path>] [--include_closed]
dctl intake get <intake-id>
dctl intake logs <intake-id> [--tail <n>] [--run_id <n>] [--follow]
```

## 前提

Issue トラッカーはプロジェクトごとに選び、`.doctrine/project.yaml` の `tracker` に書く。`project.yaml` は毎回読み直すので、書き換えてもデーモンの再起動は要らない。

```yaml
# GitHub（既定）
tracker: { kind: github }

# Linear
tracker: { kind: linear, team: ENG }
```

Linear では `states` を足してもよい。プロジェクトは登録済みであること。

GitHub を使うときの前提:

- デーモンの PATH に `gh` がある。
- `gh auth login` 済みである。
- リポジトリに GitHub の remote がある。

Linear を使うときの前提:

- 状態ディレクトリの `config.json` に `{ "linearApiKey": "lin_api_..." }` を書き、`dctld` を起動し直している。状態ディレクトリは既定で `~/.local/state/doctrine` で、`DOCTRINE_STATE_DIR` で変えられる。

前提が欠けていると、Issue を選ぶ画面に案内と「もう一度確かめる」ボタンが出る。

## Issue を選んで Intake を始める

サイドバーの「Intake」アイコンを開き、「＋」（「Issue を選んで Intake を始める」）を押す。

- 「プロジェクト」を選ぶ欄
- 「自分が担当」/「すべて」の切り替え
- 「タイトルで探す（Enter で検索）」の検索欄

GitHub のときだけ、「番号か URL を直接入れる」欄と「選ぶ」ボタンもある。Linear では、`tracker.team` のチームの開いている Issue が並ぶ。

Issue を選び、「Intake を開始」を押す。同じ Issue で開いている Intake があれば、ボタンは「進行中の Intake を開く」になる。1 つの Issue に開いている Intake は 1 つだけである。Linear では、開始すると親 Issue を進行中に進める。GitHub では Issue の状態を変えない。

## 質問と仮定に答える

エージェントは Issue とリポジトリを読むだけで、書き込めない。読むためのツールだけを渡し、リポジトリを書き換えたら、その出力は捨てて「要確認」にする。

読み終えると、論点がまとめて 1 回で届く。

- 質問: 選択肢と判断材料が付き、推奨は付かない。
- 仮定: 結論・根拠・崩れたときに変わるところが付く。

質問の種類は「単一選択」/「複数選択」/「自由記述」で、「その他（選択肢以外の答え）」と「補足・選んだ理由」の欄がある。「エージェントの仮定」は、仮定ごとに「認める」か「書き直す」を選ぶ。書き直すなら「正しい内容」を書く。

「回答を送る…」を押すと確認のモーダルが開くので、「送る」を押す。論点が無ければ、この段は飛ばして分解に進む。分解の途中で、もう一度質問が来ることもある。

## PFD をレビューして、差し戻すか承認する

画面の見出しは「N 回目の案」。左に PFD の図があり、成果物とプロセスが左から右へ並ぶ。同じ段のプロセスは並列に走る。右に要素のパネルがある。

図の印は次のとおり。

- 🔒 固定
- ◎ ゴール
- 既存
- 決定
- 人

要素を選ぶと、パネルに定義が出る。

- 成果物: 説明・確かめ方・前段・後続
- プロセス: 目的・手順・完了の条件・入力・出力

エージェントのプロセスには、「タスクのプロンプト」でタスクに渡る文面の下見もある。

差し戻すときは、要素に「コメントを足す」でコメントを付ける。計画全体へのコメントも書ける。「差し戻す…」を押し、確認のモーダルで「差し戻す」を押すと、エージェントは同じ会話の続きで直し、コメントに番号ごとに返答する。

承認するときは「承認する」を押す。承認は、そのとき表示している案の内容（ハッシュ）に対して記録される。表示中の案が最新でなければ、承認できない。

検証に通らない案は人に届かない。エージェントに返して直させ、3 回続けて通らなければ、Intake は「要確認」になる。

## 承認すると、sub-issue が作られ、プロセスが自動でタスクになる

プロセスごとに親 Issue の sub-issue を作る。GitHub でも Linear でも作り、人のプロセスにも作る。

デーモンが 2 分ごとに見張り、入力が揃ったエージェントのプロセスをタスクにする。承認の直後と「更新する」を押したときは、すぐに見る。アプリを閉じていても動く。同じプロセスが二重にタスクになることは無い。

タスクの中身は次のとおり。

- タイトルはプロセス名で、目印は付かない。
- ワークフローは、プロジェクトの既定のワークフローを使う。
- タスクのプロンプトの構成は「目的・前提・作るもの・手順・完了条件・範囲」。

sub-issue が作れていないプロセスはタスクにならない。状態は「着手可能（sub-issue 待ち）」と出る。「自動投入を一時停止」/「自動投入を再開」で、投入を止められる。

## 成果物は baseBranch へのマージで下流に渡る

下流のプロセスは、上流のタスクの PR が baseBranch にマージされるまで始まらない。マージのコミットが `origin/<baseBranch>` に載るのも待つ。`git fetch` に失敗した回は投入しない。

:::caution
`project-add` が作る既定のワークフローには、PR を作るステップが無い。PR を作るステップを足すときは、PR の本文に `{{ issue.closes }}` を入れること。PR が無いまま完了したプロセスは「要確認（PR が無い）」で止まる。
:::

sub-issue の閉じ方は、トラッカーで違う。

- GitHub: PR 本文の `Closes …` で閉じる。
- Linear: マージを見たデーモンが閉じる。

## 進み具合を見る

プロセスの状態は次のとおり。

- 入力待ち
- 着手可能: 括弧書きで「一時停止中」「改訂中」「sub-issue 待ち」が付くことがある。
- 実行中
- PR レビュー中
- マージ済み
- あなたの番
- 完了（人）
- 要確認: 括弧書きで「タスクが止まった」「PR が無い」「PR が閉じられた」が付く。

上に状態ごとの件数と「マージ済み N / M」が並ぶ。プロセスを選ぶと、パネルに状態・sub-issue・タスク・PR が出る。

## 人のプロセス

`actor: human` のプロセスはタスクにならない。入力が揃うと「あなたの番」になり、「操作が必要」の枠に出る。「決めた内容」を書いて「完了を記録する」を押す。内容は必須である。書いた内容は、下流のタスクのプロンプトの「人が決めたこと:」に載る。

## 止まったプロセスを投入し直す

次の状態のプロセスは「操作が必要」の枠に出る。

- 「要確認（タスクが止まった）」
- 「要確認（PR が無い）」
- 「要確認（PR が閉じられた）」

「再投入する」を押すと、同じプロセス・同じ sub-issue で新しいタスクを作る。前のタスクは履歴に残り、その worktree は、未コミットの変更が無ければ消す。プロセスの id を書き換える必要は無い。

## 承認した後に計画を直す（改訂）

承認した PFD は手で編集できない。「改訂に入る…」を押し、まだ固定されていない要素にコメントを付け、「改訂を始める」を押す。

- 🔒 の付いた部分は固定されたまま、残りだけが直る。🔒 の付く部分とは、タスクになった・終わったプロセスと、その入出力である。
- 新しい投入は止まる。走っているタスクはそのまま。
- 画面に「改訂中」の帯と「改訂をやめる」が出る。やめると、最後に承認した計画に戻る。

新しい案は、同じく「承認する」で承認する。

## 終わり方

末端の成果物（ゴール）がすべて揃うと「完了しました」になる。親 Issue は自動では閉じない。「Issue を閉じる」で閉じるかどうかを自分で決める。

中止するには、見出しの「中止…」から「Intake を中止する」を開く。承認の後なら、次のどちらかを選び、「中止する」を押す。

- 「そのままにする」
- 「タスクを止め、sub-issue を取りやめとして閉じる」

「要確認」になった Intake は、アプリからは中止しかできない。
